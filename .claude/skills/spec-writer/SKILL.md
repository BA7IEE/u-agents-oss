# 写规格 house-style

> 来自 `CLAUDE.md` §5「AI 操作准则」。本 skill 是把这套准则在写规格时即时拉起的检查表。

## 硬约束
1. **只产出 .md**（§0）。涉及改代码的结论 → 写成规格让用户/执行会话落地，绝不自己改。
2. **先读现状代码再写**：Read/Grep 上游源码确认事实，再下笔；规格要能 grep 到对应符号。
3. **中文正文，英文标识符**：变量名、文件路径、函数名保留英文原文，不要翻译。
4. **不擅自扩范围**：用户没问的章节别主动加——文档膨胀会稀释约束力。
5. **冲突记 TODO 不自行解决**：代码现状与规格冲突时，写进该规格的"差异 / TODO"区块，停下问用户。
6. **给可点开的定位**：文件路径 + 行号或符号名，方便非职业程序员用户直接点开看。

## 规格文件惯例
- 编号沿用 `NN-主题.md`（00–14 已用）+ 里程碑专项 `M{1,2,3}-*.md`；放 [`.planning/`](../../../.planning/)。
- 章节用 `§` 编号，方便跨文件引用（如 "02 §6.2.2"）。
- 同步差异报告进 `.planning/sync-reports/`。
- 引用其它规格用相对链接，便于点开。

## 写完自检
- [ ] 全是 .md 改动？（hook 会拦非 .md，但自己先确认）
- [ ] 每条"应改代码"的结论都有文件+符号定位？
- [ ] 没有顺手加用户没要的章节？
- [ ] 改造点相关的，是否需要同步更新 [`uapi-markers`] / §14？
