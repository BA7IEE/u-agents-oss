## 1. 8 真 P0（按严重度排）

### 🔴 P0-1（N1.F7c）web-fetch.ts redirect:'follow' — v24 修补未覆盖

[`packages/pi-agent-server/src/tools/web-fetch.ts:366`](../../packages/pi-agent-server/src/tools/web-fetch.ts) `await fetch(url, { redirect: 'follow', ... })` —— 与 v24 修的 api-tools.ts / credential-manager.ts 完全**同形态**漏洞，但**没修**！

**攻击链**：用户让 LLM 调 web_fetch tool → LLM 输 `https://attacker.com` → DNS 查 OK → fetch 时 attacker 返 302 → `http://169.254.169.254/...` → fetch follow → AWS 元数据 token 泄漏。`web_fetch` 默认开（不像 browser_tool 已 v24 关掉），LLM 任意输入触发。

**修复**：1 行加 `redirect: 'manual'` + 30x 主动拒绝（与 §3.7 #45a 同模板）+ 加 marker 加单测。

### 🔴 P0-2（N3.F1）x64 DMG 230MB 留在 release/ 是假信号

`/Users/dengwang/Documents/u-agents-oss/u-agents/apps/electron/release/U-Agents-x64.dmg` 实测内嵌 arm64 bun → 装 Intel Mac 闪退。但这文件**外观完整**，未来外部 AI 看到 release/ 目录会以为"x64 完成了"。

**修复**：(a) `electron-builder.yml:107-109` `mac.target.arch` 暂去掉 x64（源头不打），或 (b) build-dmg.sh 末尾删 x64 产物，或 (c) v0.9.2 release-notes 顶部加"x64 包未实测，疑似闪退" warning + 下载页隐藏 x64 链接。

### 🔴 P0-3（O1.F2.3）模型 ID 不前置校验 — onboarding 完，第一条消息 404

用户 onboarding 输 `gpt-5.5`（默认占位）但 Token 套餐不含 → 进主界面发第一条消息收 404 / `model_not_found` → 用户以为"软件坏了"。**onboarding 提交时只校验非空**，不查模型清单。

**修复**：02-llm-gateway-spec §2.4 把"自动模型拉取"从"可选"升 P0 / M1.5 必做。或 onboarding 提交前 `GET /v1/models` 拉 token 套餐做白名单。

### 🔴 P0-4（O1.F4.1）Intel Mac 卡 v0.9.1 + 无任何通知

D-β 决策接受了"Intel Mac 看到无可用更新"，但 Intel 用户**完全不知**：(a) v0.9.2 已发布、(b) 含 SSRF 安全修复、(c) 含 Pi 系统 prompt 修复等多项体验提升。R2 上无"未公布 release"页让用户手动选 arch 下载。**P1（O2.F3）扩散**：Intel 用户停留 v0.9.1 = 不受 v24 SSRF 真修保护。

**修复**：(a) 推 Intel Mac 实测（云 Mac 或借机）尽快出 x64 包；(b) 在 agents.u-studio.cn 下载页加"全平台版本归档"链接到 `/v0.9.2/`；(c) Intel 用户启动时 in-app banner 提示。

### 🔴 P0-5（O1.F4.4）auto-update.ts 注释残留旧 URL

[`apps/electron/src/main/auto-update.ts:5`](../../apps/electron/src/main/auto-update.ts) 注释 `https://u-agents.u-studio.cn/electron/latest`，但 `electron-builder.yml:93` `publish.url = https://update.u-agents.u-studio.cn/latest`（独立 subdomain + 无 `/electron`）。**两处不一致** = 排错时读注释会被误导。

**修复**：1 行改注释。`01-branding-spec.md §2.7` 范围内但实际未改。

## 2. P1 关键 21 项汇总

### 2.1 SSRF 面（N1，5 项 — 这是 v24 视角盲区）

v24 把 SSRF 看成 2 个点（api-tools + credential-manager），但实际是个**面**：

| 调用点 | 问题 | 风险 |
|---|---|---|
| `web-fetch.ts:366` | redirect:'follow'（已升 P0-1） | 高 |
| `source-test.ts:590,648,654,661` | 4 处无 SSRF guard，1 处带 bearer token | 高 |
| `webhook-utils.ts:244` | 自动化 webhook 仅 scheme 检查 | 中（LLM 可写）|
| `oauth.ts:471,513` token_endpoint 来自 metadata | 无校验，PKCE code 可泄漏 | 高 |
| `generic-oauth.ts:108,171` | tokenEndpoint 无 guard，refresh_token 泄漏 | 中 |
| `drivers/pi.ts:65,198` + `anthropic.ts:50` | 自定义 baseUrl 无 guard | 中（pi_compat 锁后减半）|
| `oauth.ts isUrlSafeToFetch` vs url-safety.ts | 3 套实现，oauth 缺 IPv6 ULA + cloud metadata 域名 | 中（碎片化）|
| **DNS rebinding** | 自承缺口未补，主路径无防御 | 中 |

**建议**：M3 起一个 `M3-SSRF-CONSOLIDATION` 任务把 url-safety.ts 升为唯一 helper（增 DNS lookup），全仓接入。
