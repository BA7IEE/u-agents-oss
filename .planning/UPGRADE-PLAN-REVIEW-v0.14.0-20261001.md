## 2. 逐项发现与修订要求

### R1 — 在读取存储密钥前，固定并验证连接测试的目的地

**证据。** 本地 `packages/server-core/src/handlers/rpc/llm-connections.ts:317` 起的 `TEST_LLM_CONNECTION_SETUP` 只有 `provider === 'pi' && normalizedBaseUrl === U_API_BASE_URL` 才进入专用发现分支；其他输入可进入后面的通用 `testBackendConnection`。本地 `packages/server-core/src/domain/connection-setup-logic.ts:65` 的校验只检查路由参数是否完整，并非 U-API 域名白名单。

[上游测试处理器](https://github.com/craft-ai-agents/craft-agents-oss/blob/73bd9c2a3573158bea880984eb8d5fdb41e0cac2/packages/server-core/src/handlers/rpc/llm-connections.ts#L331) 在 337–347 行通过 slug 取得存储密钥，随后把调用方提供的 provider/baseUrl 等继续用于测试。[密钥解析函数](https://github.com/craft-ai-agents/craft-agents-oss/blob/73bd9c2a3573158bea880984eb8d5fdb41e0cac2/packages/server-core/src/domain/connection-setup-logic.ts#L128) 本身不检查目的地。

**为什么现有要求不够。** “合法 slug”不能证明其凭证可以发送到调用者给出的地址。按方案逐段移植，可能出现合法 U-API slug + 掩码 + 外部 baseUrl 落入通用测试分支的组合。G04 目前明确写的是重启和保存，不能代替保存前测试 RPC 的约束。这里是合并风险推演，尚未执行请求复现。

**修订。** A.1 必须明确：先校验产品允许的连接种类及输入，存储凭证只能用于该连接的受信固定目的地；U-API 测试从服务端构造网关与路由，不让 renderer 参数选择密钥去向。新输入密钥的测试也服从同一模型出口政策。禁止组合应在凭证读取/探活前拒绝，不能用“之后保存会归一”补救。

**新增验收。** 对三个合法 slug 分别组合掩码、外部 HTTPS、loopback、非允许 provider、缺失连接；断言禁止路径没有网络请求，最好同时断言未访问凭证库。正常掩码测试仍能完成固定网关发现；不得把真实 Token 放入测试日志。

### R2 — 配置副本不等于隔离运行副本

**证据。** 本地 `packages/shared/src/config/storage.ts:294` 起直接展开 `workspaces[].rootPath`；309–311 行会按该路径补建目录。多个 workspace 配置写入也使用该 rootPath。`packages/server-core/src/sessions/SessionManager.ts:1578` 明确说明在启动时为所有工作区初始化自动化/调度相关服务。数据根环境变量不会自动改写这些业务路径。

**触发情况。** W0 复制 config 与 workspace 后，如果 config 仍保留原来的绝对路径或 `~` 路径，候选版本仍可访问正式工作区。即使重映射了工作区，旧自动化、脚本、Sources 和附件引用也可能指向外部路径或服务。方案 D01 的“全部在同一隔离根”还容易被误读成强制改变产品支持外置 workspace 的正常行为。

**修订。** 区分两个对象：①供恢复用的原样停机备份；②供演练用的脱敏、重映射运行副本。备份不做改写。演练副本应在首次启动前列出并验证 config→workspace、session workingDirectory、附件、脚本等路径映射；不能仅替换一个环境变量。使用无真实凭证的 fixtures，首次迁移演练默认阻断外发并暂停任务/自动化执行。需要验证恢复调度时，在专门的 mock 环境解除限制。

不要因此要求所有真实 workspace 移入 config 根；要求的是演练可写路径均属于明确允许的副本集合，外部引用有逐项处理结果。没有受控运行条件时只做静态比较，不能先启动再观察。

**新增验收。** 放入仍指向原路径的故意错误 fixture，启动前校验必须失败；演练前后正式目录内容清单不变，网络 mock 无意外请求。另测带外置 workspace 的合法配置，保证产品路径能力没有被误删。

### R3 — 模型默认值和图片能力的“保留”不是当前刷新实现的完整事实

**证据。** 本地 `packages/server-core/src/domain/u-api-model-discovery.ts:235` 的 `resolveUApiRefreshSelection` 只接收 defaultModel、modelIds、customEndpointApi。它把“当前默认值等于旧目录第一项”解释为跟随自动推荐；这种情况下即使旧默认仍存在，也会跟随新的推荐。对应上层 `packages/server-core/src/model-fetchers/index.ts:88` 起把原 models 简化为 ID，再用新 selection 覆盖 models/customEndpoint。

同文件 `resolveUApiModelSelection` 在 197–227 行构造字符串模型列表，并设置 `customEndpoint.supportsImages: true`。这个刷新链没有传入并保留逐模型能力覆盖值。因此 A.3 不能写成“保留现有图片 override 合同”，G03 也不能笼统要求所有仍在目录的默认值不变。

**影响。** 原方案同时承诺保持现状与改变现状。实施者可能按现有自动推荐行为交付却被 G03 判错，或者按方案新增能力合并，却把它当成上游同步的无行为变化部分。

**修订。** 将其拆为“兼容既有推荐/手动选择规则”和“是否补齐能力覆盖值在刷新中的保留”。后者应登记为已有缺口及本轮建议修复，明确优先级、模型消失后的清理规则和协议切换规则；不要声称已经存在。沿用当前自动推荐判定时，需明示其无法区分用户主动选择第一项与自动选择第一项，不随手增加新的持久化状态。

**新增验收。** 至少分别测试自动推荐切换、手动非首项仍可用、旧模型消失、单模型图片覆盖关闭、连接级图片关闭、协议变化。对于能力覆盖保留，先给出预期合并规则再写断言，避免把新设计伪装成回归测试。

### R4 — Pages 页面摘要没有覆盖被授权脚本的字节内容

**证据。** [storage.ts](https://github.com/craft-ai-agents/craft-agents-oss/blob/73bd9c2a3573158bea880984eb8d5fdb41e0cac2/packages/shared/src/pages/storage.ts#L414) 的摘要来自传入的页面内容字符串；439–459 行在保存 index.html 时更新它。[validation.ts](https://github.com/craft-ai-agents/craft-agents-oss/blob/73bd9c2a3573158bea880984eb8d5fdb41e0cac2/packages/shared/src/pages/validation.ts#L169) 的 grant 绑定这个 contentDigest；script 描述包含路径、runtime、args，没有脚本文件摘要。[action-bridge.ts](https://github.com/craft-ai-agents/craft-agents-oss/blob/73bd9c2a3573158bea880984eb8d5fdb41e0cac2/packages/shared/src/pages/action-bridge.ts#L302) 检查页面/lease/grant 的摘要，373–376 行的 script 匹配不校验脚本内容。

**影响。** 页面 HTML 不变、同路径脚本文件被修改时，不能凭上述摘要机制推断授权自动失效。原方案 F2 的“内容变化失效授权”表述过宽；F3 的后台刷新也不能靠 F2 的交互授权测试间接验收。这个事实不等于上游承诺了不可变脚本后违反承诺，更不等于已证明远程攻击；问题在于本方案尚未定义授权的是路径能力还是具体脚本版本。

**修订。** 将 F03 精确写为“HTML 内容变化使既有页面授权失效”。对 script 单列产品语义：若接受路径能力，需明确同路径脚本变化仍可能执行；若要求版本授权，则需独立设计内容变更后的重新授权，并考虑依赖文件，不能只加入口文件 hash 就宣称完整沙箱。不要把这项新增机制默默塞进同步。

在语义未定之前，建议首个候选关闭 F2 script 与 F3 调度入口，只验收其余已明确能力；这是建议，并非当前已修改产品范围。若本轮保留，则增加“改脚本不改 HTML”“依赖文件变化”“无页面打开时刷新”“撤销/禁用后的下一次调度”用例，分别证明预期行为。

### R5 — 工作包不是当前写法暗示的独立完成顺序

**证据。** W1 要求“无未解决冲突”“功能默认不外放”；W2 才完成决策与分享政策，W3/W4 才明确高冲突权限与收费代码的适配。SessionManager 等交叉文件在结束真实 merge 前就必须选择解决内容。上游新分享默认开放，不能把“后续会关”当 W1 已满足的默认状态。

**影响。** 执行者可能为完成 W1 先用临时取舍结束合并，再在 W2–W4 修正，形成未经审查的可运行中间版本。方案虽已提醒中间提交不一定可发布，仍未规定什么时候允许启动迁移或接入正式数据。另，214 行把 copier 写成 electron-build-main.ts 的下游子调用不准确：dmg 流程中是构建后另行调用 copier；应画出真实调用关系以免误删入口。

**修订。** 把 W1 改为覆盖 W2–W7 相关设计的“集成容器”，冲突映射按模块记录；或将 W1 的完成条件改成清单与依赖设计就绪，不假装 merge 已结束。结束 merge 的条件应是关键冲突均按既定合同解决。首次启动之前，政策限制、配置根、网络保护和收费隔离必须到位；安装包验收仍放在最终候选。先做完整依赖/构建静态核查，干净构建可以早失败，不必等 Pages 行为验收结束才发现链路断裂。

## 3. 其他维度的复核结论

| 维度 | 本轮判断 | 仍需实施证明的边界 |
|---|---|---|
| 版本选择/差异规模 | 固定三方 SHA、一次同步后分包适配合理 | 561 文件清单和 102 交叉候选不是实际 merge 冲突或工时承诺 |
| 权限继承与管理员审批 | 方案保留两套不同授权含义，方向正确 | TaskRunner、Automation 与子会话入口要分别测；不能拿一个 clamp 覆盖全部 |
| 付费生图 | message 身份、owner、claim 后不重发等边界应保留 | 上游普通 retry 与我方付费上下文是否正确组合，仍需行为测试 |
| 决策模型/Guarded | 已识别 skipGates、语义条件默认继续等关键问题 | 所有宿主入口、旧配置与有效权限必须实际验证，不能仅查 UI |
| API/OAuth | 把地址保护迁到共用请求层、区分 Sources 与模型出口合理 | 不扩大声称 DNS rebinding 已解决；实际 OAuth 回调需专门环境验收 |
| 数据回退 | 不承诺直接降级、保留升级后数据正确 | R2 修订后才具备可信演练前提；恢复不等于自动合并新旧数据 |
| 构建/更新 | 识别旧 helper 缺产物、跨架构缓存和更新 hook 很必要 | 打包成功、旧版本更新成功、平台实测分别记录 |
| 中文/品牌/法律 | 集合比较、内部协议例外、保留版权证据合理 | 不能以翻译 key 检查代替实际页面和功能承诺核对 |
| 发布范围 | 候选、平台可用、公开发布分开合理 | Pages/script 尚无明确取舍时不能默认为整套开放 |
